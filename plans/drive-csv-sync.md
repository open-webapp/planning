# Drive CSV Sync — Replace Sheets Backend with Google Drive CSV — Implementation Plan

Source of truth: this doc + real current source. Line refs point at current files as of this writing (2026-08-02) — re-check line numbers before editing if other work has landed first. No `plans/_template.md` exists in this repo; this plan follows the structure/style of `plans/projects-app-sync.md`, the original (already-implemented) Sheets sync plan that this feature supersedes.

## Overview

Replace the Google Sheets storage backend for two-way sync with a single CSV file stored on the user's Google Drive, in an app-owned nested folder (`OpenWebApp/Planning`). Keep the entire bidirectional 3-way-merge engine in `src/lib/sync.ts` (`diffAgainstSnapshot`, `threeWayMerge`, `applyResolutions`, `syncNow` orchestrator) — only the I/O layer underneath it changes, from Sheets values:batchGet/batchUpdate to Drive files.get/multipart-upload/media-upload. Drop every Sheets-specific code path: `ensureSheetTabs`, `pullFromSheet`, `pushToSheet`, the `spreadsheets` OAuth scope, the spreadsheet-ID input in Settings, and the dead legacy `SYNC_STARTED`/`operation: 'backup'|'restore'` middleware branch in `App.tsx` that talks to Sheets directly.

Also unify the CSV format: the same `buildTasksCsvString` in `src/lib/csv.ts` now serves both the local "Export CSV" download and the Drive-synced file, with a new `ID` column first and `Dependencies` now holding ids instead of names. Filename convention changes from `<slug>-tasks.csv` to `<slug>.csv` so the local download and the Drive file are named identically.

**Not in scope / explicitly dropped:** a separate Milestones-tab-equivalent. Milestones are derived purely from each task's Milestone name column, exactly like today's CSV export — see "Notes / accepted tradeoffs" below for the fidelity loss this implies and why it's accepted.

**No data migration:** existing `Project.spreadsheetId` values are simply abandoned. `Project` gets a new `driveFileId: string | undefined` field; there is no code path that reads an old `spreadsheetId` to auto-create a matching Drive file. Users reconnect manually via the new "Connect to Google Drive" button.

## Phase 2 — Drive API module

Can start in parallel with Phase 1; Phase 3 depends on both.

10. **Add Drive-file I/O functions to `src/lib/googleAuth.ts`.** Keep this file as the single OAuth+API module (matches the existing pattern — don't split into a new file, per the existing precedent of `pullFromSheet`/`pushToSheet` living alongside token logic). Add:
    - `findOrCreateFolder(name, parentId, token)`: `GET https://www.googleapis.com/drive/v3/files?q='<parentId>' in parents and name='<name>' and mimeType='application/vnd.google-apps.folder' and trashed=false&fields=files(id,name)` (root parent uses `'root' in parents` when `parentId` is undefined); if `files` array empty, `POST https://www.googleapis.com/drive/v3/files` with body `{ name, mimeType: 'application/vnd.google-apps.folder', parents: [parentId || 'root'] }`. Returns the folder id either way.
    - `ensureAppFolder(token)`: calls `findOrCreateFolder('OpenWebApp', undefined, token)` then `findOrCreateFolder('Planning', <that id>, token)`, returns the innermost (`Planning`) folder id. Mirrors `ensureSheetTabs`'s "find or create" shape (currently lines 254-319) but for folders instead of tabs.
    - `createDriveCsvFile(filename, csvContent, folderId, token)`: multipart upload per requirement 10 — `POST https://www.googleapis.com/upload/drive/v3/files?uploadType=multipart` with a `multipart/related` body (JSON metadata part `{ name: filename, parents: [folderId], mimeType: 'text/csv' }` + CSV content part). Returns the new file's `id`.
    - `updateDriveCsvFile(fileId, csvContent, token)`: media upload — `PATCH https://www.googleapis.com/upload/drive/v3/files/<fileId>?uploadType=media`, body = raw CSV text, header `Content-Type: text/csv`.

    All functions follow the existing raw-`fetch` + `Authorization: Bearer <token>` pattern already used throughout this file (see `ensureSheetTabs` lines 258-263, `pullFromSheet` lines 344-348) — no SDK. ## Notes / accepted tradeoffs

1. **Milestone fidelity is intentionally degraded vs. the old Sheets Milestones tab.** The Sheets-era design (see `plans/projects-app-sync.md` Phase 2) stored milestones purely as a plain-text name column on each task row too (it never had a truly separate Milestones tab in the shipped implementation — see `pullFromSheet`'s doc comment at `googleAuth.ts` lines 321-328), so this plan is *not* actually a regression from what's currently implemented; it's continuity with the existing Sheets sync's own milestone model, carried over unchanged into CSV. Restating the accepted behavior explicitly since the task brief calls it out: milestone identity is reconstructed by name-matching on every pull (task 8), so renaming a milestone in the CSV/Drive file and renaming it in the browser simultaneously will not "merge" as a rename — it'll look like a new milestone appearing and the old one's tasks losing their milestone link, then reconverging next sync once names agree again. Milestones with zero tasks are invisible to sync entirely (never written to the CSV, so a browser-only empty milestone won't round-trip). This is a shared, accepted limitation of a name-keyed milestone model, not a new bug introduced by this migration.
2. **No data migration for `spreadsheetId` → `driveFileId`.** Existing projects with a `spreadsheetId` set simply stop showing the (now-removed) spreadsheet UI; their `driveFileId` starts `undefined` and the CloudSync icon disappears until the user clicks "Connect to Google Drive" again. Their old Sheets data is not read, ported, or referenced anywhere in the new code. No task in this plan writes a migration path — this is deliberate per the resolved requirements, not an oversight.
3. **`connectDriveSync`'s first-connect file seed uses whatever the browser currently has.** There's no "pull-before-create" step — connecting Drive sync on a project with existing local tasks pushes them straight into a freshly created CSV, exactly mirroring the old Sheets flow's first-sync-from-empty-sheet case (`snapshot === null` ⇒ everything treated as browser-added).
4. **`SyncConflict.sheetValue` → `driveValue` rename (task 2/16) is optional polish, not load-bearing.** If time-constrained during implementation, this rename can be skipped and the field left as `sheetValue` internally (only user-facing overlay copy, task 24, actually needs to say "Drive" instead of "Sheet") — flagging so whoever implements can descope task 2/16 without breaking anything else in this plan if needed.

## Risks / open judgment calls

1. **Drive `files.list` `q` query eventual consistency.** Drive API's `files.list` search (used by `findOrCreateFolder`, task 10) is not always immediately consistent after a `files.create` — a rapid disconnect-then-reconnect-then-immediately-sync sequence could theoretically race and create a duplicate `OpenWebApp` or `Planning` folder. Low risk for this app's click-triggered (not polling) sync model, but worth a code comment at the call site; no automated test can easily cover this without a real Drive account or a much heavier mock.
2. **CSV as a "database row format" is fragile to manual spreadsheet-app edits.** If a user opens the Drive CSV in Google Sheets/Excel and it auto-reformats a date, or the app adds a trailing newline/BOM that `papaparse` doesn't expect, parsing could silently drop rows. `papaparse`'s `header: true` mode is fairly tolerant, but recommend a defensive test (task 9's "malformed column" case) and treating any row missing an `ID` value as unparseable/skipped rather than crashing the whole sync.
3. **`updateDriveCsvFile`'s media-upload PATCH doesn't re-verify the file wasn't renamed/moved by the user in Drive.** Since scope is `drive.file` (app-created files only), the app can still write to a file it created even if the user renamed it in the Drive UI — the write will succeed but the file's *name* will drift from `getCSVFilename(project.name)` after a project rename in-app. Not fixed by this plan; `driveFileId` is the source of truth for *which* file, not enforcing name sync back onto Drive. Acceptable given no requirement asked for it, but flagging since it's a slight behavior difference from "identical name always" framing in requirement 6 (that requirement is about the *initial* created name matching the local download name, not an ongoing invariant).
4. **Removing the dead `SYNC_STARTED`/`operation` branch (task 21) touches `App.tsx`'s dispatch middleware, a shared chokepoint.** Double-check no other action creator anywhere in the codebase still dispatches `{ type: 'SYNC_STARTED', operation: 'backup' | 'restore' }` before deleting the branch — a grep for `operation:` across `src/` as a pre-check is cheap insurance (the research for this plan found no such call site outside the dead branch itself, but re-verify at implementation time since other work may have landed).
5. **Task 2/16's `sheetValue`→`driveValue` rename is a pure-cosmetic ripple across `sync.ts`, `types.ts`, `sync.test.ts`, and the conflict overlay.** If it turns out `SyncConflictOverlay.tsx` (not read in detail while writing this plan — confirm its contents before task 24) accesses the field by a different pattern than expected, this rename could touch more call sites than estimated. Descope per tradeoff note 4 above if it balloons.
